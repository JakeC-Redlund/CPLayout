## First RTK Review

The new `nmeaSafety.test.ts` initially reproduced 13 failing cases. They exposed stale-fix fallback after malformed/positionless GGA, single-axis/missing-axis GST estimates, permissive numeric parsing, non-finite or negative quality values, invalid configuration, future/non-finite reception clocks, invalid positions, incomplete/non-measured RMC, stale time-of-day joins, incorrect height-unit assumptions, unbounded stream carry, malformed headers, and invalid-fix point creation.

The corrected implementation:

- Treats the newest GGA as authoritative for availability; it cannot fall back to an older valid position.
- Requires decimal coordinates/measurements, valid ranges, finite quality thresholds, and a usable fix even if the configured minimum is `invalid`.
- Computes a new GST horizontal estimate as `hypot(latitude sigma, longitude sigma)` only with both valid components. The receiver panel labels it `Horizontal RMS`. This is not measured accuracy or a 95% confidence radius; previously stored estimates are not rewritten or reclassified.
- Requires present matching RMC evidence to be active, dated, coordinate-consistent, and from an allowed measured mode. GGA/GST without RMC remains supported, without a receiver-date claim.
- Bounds GGA-to-GST/RMC reception skew to 2,000 ms and incomplete sentence carry to 1,024 characters. These are CPLayout defensive policies, not universal receiver specifications. Receiver-specific profiles require captured fixtures before changing them.
- Retains first-reception time for repeated epochs within a session, including beyond the rolling sample window. A new session or explicitly dated next-day epoch may start a new receipt age.
- Re-evaluates quality/age at each survey or geometry capture command, independently of the display timer. Newly captured survey quality includes correction age at capture time.
- Clears capture eligibility immediately on disconnect/error. Invalid-fix recovery cannot refresh an earlier epoch merely by replaying it.

## Initial Review Findings

The following findings describe the pre-correction state. Their later disposition is recorded in the integrated checkpoints; unresolved CRS/ground-scale and hardware issues remain open. They must not be hidden behind the first packet's passing tests:

- `packages/core/src/coordinates.ts` extracts numeric substrings rather than validating the complete coordinate input; scientific notation can be split into unrelated numbers. Its DMS/DDM formatters also need carry/round-trip checks at degree boundaries.
- Receiver coordinate quantization is separate from GST uncertainty. [NovAtel's precision table](https://docs.novatel.com/OEM7/Content/Logs/GPGLL.htm) documents different decimal precision for GGA and RMC. Add a resolution budget and source-backed agreement tolerance; do not simply relax coherence checks or assume a small GST value makes rounded coordinates centimetre-accurate.
- `packages/core/src/units.ts` permits Web Mercator as a project CRS. [PROJ's definition](https://proj.org/en/stable/operations/projections/webmerc.html) has latitude-dependent scale; projected grid metres must not silently be treated as ground measurements. Review warnings, supported analysis CRSes and an explicit migration workflow without reinterpreting saved XY values.
- The same CRS whitelist uses overbroad numeric ranges for NAD27/NAD83 UTM. Local PROJ 9.4.0 metadata identifies accepted `EPSG:26741` as NAD27 / California zone I in US survey feet, and `EPSG:26929` as NAD83 / Alabama East, not UTM zone 29. New coordinate transformations must not infer a UTM definition from these code suffixes. Existing project XY must be preserved for explicit compatibility review, not silently rescaled or reinterpreted.
- `evaluatePathBoundaryDistance` labels a full-circle center-to-boundary-minus-radius value `exact_full_circle`. Verify the distinction between containment margin and signed point-to-boundary distance after a circle exits a concave field. Partial-circle negative-distance extrema also need an independent oracle, not just tests derived from the implementation's candidates.
- The current serial transport tests use a permissive `port.close()` mock. Add real stream-lock assertions and cancellation/concurrent-operation tests before claiming reliable cleanup.

Historical read-only counterexamples reproduced before the fixes below:

- Projected input `1e6,4.5e6` became `{x: 1, y: 6}`. Formatting latitude `39.999999999` as DMS emitted 60.00 seconds, which the parser then rejected. These failures required complete-input validation and carry-safe formatting.
- For center `(1,1)`, radius `3`, counterclockwise 0-to-90-degree sweep and boundary `[(0,0),(4,0),(4,2.5),(1.5,2.5),(1.5,4),(0,4)]`, the partial-clearance candidate method returns `-1.051952 m`; the concave-notch bisector gives `-1.061552813 m`. This underestimation scales with the geometry. Add an independent analytic regression and an exact or explicitly error-bounded method.
- A synthetic Web Serial readable stream paused at a yielded byte event remains locked when `session.close()` calls `port.close()`. The latter rejects; a later close attempt silently returns because `closed` is already set. The regression must assert both lock release and completion/retry semantics, not merely a close-call count.
- `ui:test:stop` terminated the recorded npm parent but left its previously verified tsx/server children running. The old process still served `.mjs` as octet-stream. The known child PIDs were checked against the prior process tree and stopped through the repository ownership-check helper, then the launcher restarted normally. Improve process-tree cleanup and verify port release before deleting ownership metadata; do not kill unverified listeners.

Independent numerical comparison used installed PROJ 9.4.0 `cs2cs` with `PROJ_NETWORK=OFF`, `--no-ballpark`, `--only-best=yes`, and explicit EPSG:4326 latitude/longitude input order. All 168 synthetic WGS84-to-UTM fixtures agreed with the installed Proj4 implementation to within `4.52e-9 m`. The fixtures span selected north/south zones, latitudes and central-meridian offsets. This is numerical implementation agreement, not a claim of physical accuracy, datum-grid availability or support for other CRSes.
