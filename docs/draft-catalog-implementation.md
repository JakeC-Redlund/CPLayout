## Storage and Compatibility

**Web:** migrate to one versioned workspace envelope containing catalog, unchanged legacy project document strings and draft documents. Read and validate the latest envelope inside a named Web Lock, apply expected-revision checks, and commit the complete mutation with one `setItem`. All writers, including legacy rename/save/delete paths, must participate. If locking or storage is unavailable, retain editing/recovery export and report persistence unavailable. Do not claim a process-local promise queue protects multiple tabs.

The HTML storage standard does not provide cross-agent locking, and quota/security failure must be surfaced. The proposed named lock uses the Web Locks API, which is exposed in secure contexts; test actual target origins and two-tab behavior before acceptance. Both primary sources were refreshed on 2026-09-14. Web Locks remains a W3C Working Draft and is cooperative: unrelated old-version writers are not protected by a new lock name. This is an implementation decision inferred from these primary sources, not an assertion of runtime proof. [HTML storage](https://html.spec.whatwg.org/multipage/webstorage.html), [Web Locks](https://www.w3.org/TR/web-locks/).

**Native:** migration 12 adds the design kind, revision and draft JSON while preserving existing design rows, timestamps, tombstones, indexes and foreign keys. Require exactly the selected project or draft payload. Legacy snapshots stay byte-preserved. Use one existing exclusive transaction scope for payload, catalog and ownership validation; correct the legacy split save in the same storage packet. Expo's API commits or rolls back the task and requires queries through its transaction object; competing writes can fail with a lock error that must remain retryable. [Expo SDK 55 SQLite](https://docs.expo.dev/versions/v55.0.0/sdk/sqlite/#withexclusivetransactionasynctask).

**Migration and rollback:** preserve original web strings and a consistent native backup before writes. Invalid JSON, duplicate ownership, orphaned references and unknown versions produce recovery diagnostics, not normalized deletion. Refuse newer schemas before mutation. New readers support old data; old installed applications are not made safe writers for the new store. Downgrade requires exporting subsequent work before restoring a compatible backup. Do not delete old keys or backups during acceptance.

**Archives:** retain project ZIP v1. Add a distinct draft archive with validated manifest and `draft.json`, no fabricated `project.json`, calculated products, client contacts or machine-local paths. Import into an explicitly selected field map using a fresh identity and atomic create. Keep corrupt legacy bytes available only as opaque recovery data, never as a valid project or draft. Refuse unsupported versions without discarding bytes. Archive v2 Layout sessions remain a separate packet.
